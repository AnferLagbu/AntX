## 一、Critical 级别问题 (92 项)

> **定义**: 可能导致内核崩溃、数据永久损坏、安全沙箱逃逸或静默数据损坏的问题。

### 1.1 内存管理子系统 (14 项)

#### C1. 伙伴分配器 order-8 越界写入（kmalloc_slab.rs）
- **文件**: `src/kernel/mm/kmalloc_slab.rs`
- **描述**: 伙伴分配器在 order 达到 8（最大 order）时，`buddy_offset()` 计算可能溢出，返回越界的 buddy 索引，导致释放相邻页时错误合并，造成已分配页被回收后 UAF。
- **影响**: 内核堆损坏、随机崩溃
- **修复建议**: 在 `buddy_offset()` 中添加 order 边界检查，拒绝 order > MAX_ORDER 的请求。

#### C2. Slab 分配器 double-free 检测缺失（slab.rs）
- **文件**: `src/kernel/mm/slab.rs`
- **描述**: `slab_free()` 不做 double-free 检测，仅依赖 bitmap 标记位。若调用方 double-free，slab 对象被立即放回空闲链表，而之前的持有者仍可使用。
- **影响**: UAF、信息泄露、潜在 RCE
- **修复建议**: 在 `slab_free()` 中检查 bitmap 位，若已为 0（已空闲）则 panic 或返回错误。

#### C3. VMM 页表更新缺少 TLB 刷新（vmm.rs）
- **文件**: `src/kernel/mm/vmm.rs`
- **描述**: 修改页表条目后，未执行 `invlpg` 刷新对应地址的 TLB。x86 在未 flush TLB 的情况下，后续对同一虚拟地址的访问可能读取到旧映射。
- **影响**: 随机内存访问错误、COW fork 后父子进程共享物理页
- **修复建议**: 每次修改页表条目后立即调用 `invlpg(addr)`。

#### C4. page_fault handler 中的递归风险（page_fault.rs）
- **文件**: `src/kernel/mm/page_fault.rs`
- **描述**: 缺页处理在栈上分配数据，如果栈页面本身引发缺页（内核栈未映射或交换），将产生嵌套 page fault 直至三重故障。
- **影响**: 内核三重故障（Triple Fault）→ 系统重启
- **修复建议**: 为 page fault handler 使用独立的内核栈（IST 栈），或预先固定映射内核栈页。

#### C5. COW fork 引用计数竞态（cow.rs）
- **文件**: `src/kernel/mm/cow.rs`
- **描述**: `cow_dec_ref()` 中先读取 refcount，再递减，中间无原子保护。多核并发 fork/exit 可导致 refcount 下溢（从 0 减到 UINT_MAX），使页永不释放。
- **影响**: 物理内存泄漏、refcount 下溢后页面被过早释放（UAF）
- **修复建议**: 使用 `fetch_sub(1, Ordering::AcqRel)` 原子操作，CAS 循环保护。

#### C6. kmalloc 大对象分配绕过（kmalloc.rs）
- **文件**: `src/kernel/mm/kmalloc.rs`
- **描述**: 请求大于 slab 最大对象大小的分配直接调用底层 PMM，但未记录该次分配的来源。后续 `kfree()` 无法判断该内存来自 slab 还是 PMM，可能错误释放。
- **影响**: 内存泄漏或 PMM 元数据损坏
- **修复建议**: 在大对象 header 中保存分配来源标记。

#### C7. VMA 合并逻辑段重叠风险（vma.rs）
- **文件**: `src/kernel/mm/vma.rs`
- **描述**: VMA 树插入时的合并逻辑仅检查 `prev.end == new.start` 或 `next.start == new.end`，但不检查权限一致性和类型一致性。可能导致不同权限的相邻 VMA 被错误合并。
- **影响**: 权限提升（可写的匿名映射与只读文件映射合并）
- **修复建议**: 合并前比对 flags/prot/type 字段。

#### C8. PMM 物理页分配零初始化不正确（pmm.rs）
- **文件**: `src/kernel/mm/pmm.rs`
- **描述**: `pmm_alloc_page()` 返回的物理页声称"已零初始化"，但实测表明某些路径（从回收链表分配时）未执行清零，导致信息泄露。
- **影响**: 内核信息泄露给用户态
- **修复建议**: 统一在 `pmm_alloc_page()` 返回前执行 memset(0)。

#### C9. VMM 高半区地址转换错误（vmm.rs / vmm_aarch64.rs）
- **文件**: `src/kernel/mm/vmm.rs`, `src/kernel/mm/vmm_aarch64.rs`
- **描述**: `phys_to_virt()` 函数在 x86_64 上使用 `| KERNEL_BASE`，但 KERNEL_BASE 值与链接脚本中的实际偏移不一致（`0xFFFF800000000000` vs `0xFFFF800001000000`）。
- **影响**: 访问到错误的虚拟地址，可能导致页表损坏
- **修复建议**: 统一 KERNEL_BASE 常量定义，从链接脚本导出符号。

#### C10. kmalloc_slab 中的整数溢出（kmalloc_slab.rs）
- **文件**: `src/kernel/mm/kmalloc_slab.rs`
- **描述**: `slab_create()` 中 `size = 1 << (order + PAGE_SHIFT)` 在 order=31 时溢出（Rust release 模式下 panic）。
- **影响**: 内核 panic（DoS）
- **修复建议**: 添加 order 上限检查（order ≤ MAX_ORDER）。

#### C11. 内存分配器双路径不一致（memory_allocator.rs）
- **文件**: `src/rust/src/memory_allocator.rs`
- **描述**: `alloc` 在 kmalloc 失败时回退到 `pmm_alloc_page()`（分配整页），但 `dealloc` 无法区分分配来源，对回退路径分配的 < PAGE_THRESHOLD 内存错误调用 `kfree()` 而非 `pmm_free_page()`。
- **影响**: slab 元数据损坏
- **修复建议**: 在分配 block 前保存来源标记，dealloc 时据此选择释放路径。

#### C12. KERNEL_BASE 常量不一致（memory_allocator.rs）
- **文件**: `src/rust/src/memory_allocator.rs`
- **描述**: `KERNEL_BASE` 在 memory_allocator.rs 中定义为 `0xFFFF800000000000`，而链接脚本中使用 `0xFFFF800001000000` 作为 VMA 基址。
- **影响**: 高半区地址转换错误
- **修复建议**: 从链接脚本导出符号，或使用统一的常量定义文件。

#### C13. VMM 四级页表遍历无边界检查（vmm.rs）
- **文件**: `src/kernel/mm/vmm.rs`
- **描述**: `vmm_walk()` 遍历页表时假设所有中间级页表都存在，但不检查 P 位（present bit），可能在中间级页表未分配时访问空指针。
- **影响**: 内核 page fault
- **修复建议**: 逐级检查 P 位，缺失时按需分配（demand paging）或返回错误。

#### C14. 物理内存管理器并发不安全（pmm.rs）
- **文件**: `src/kernel/mm/pmm.rs`
- **描述**: `pmm_alloc_page()` 和 `pmm_free_page()` 操作全局 buddy bitmap，但无锁保护。SMP 环境下并发分配/释放会导致 bitmap 损坏。
- **影响**: 双分配（两个 CPU 分到同一物理页）、内存泄漏
- **修复建议**: 使用 SpinLock 或 atomic 操作保护 buddy bitmap。

### 1.2 进程管理子系统 (13 项)

#### C15. CFS 调度器 vruntime 计数器泄漏
- **文件**: `src/kernel/proc/cfs.rs`
- **描述**: CFS `cfs_tick()` 调用 `enqueue`/`dequeue` 时更新 `total_weight`，但若进程在 enqueue 后崩溃/退出，对应的 weight 不会从统计中移除，导致后续时间片计算比例失真。
- **影响**: 调度不公平、有些进程永远得不到 CPU
- **修复建议**: 在进程退出路径中确保调用 cfs 的 dequeue 清理。

#### C16. context_switch 中的 CR3 切换无 TLB flush
- **文件**: `src/kernel/proc/switch.asm`
- **描述**: 切换进程时写入 CR3（加载新页表），但 x86 规范要求在切换页表后可能需要对全局页做 INVLPG。若新老进程共享某些全局映射，旧 TLB 条目可能残留。
- **影响**: 跨进程内存泄露（一个进程读到另一个进程的数据）
- **修复建议**: 在 CR3 写入后添加 `invlpg` 或设置 CR4.PGE 相关处理。

#### C17. ELF 加载器对畸形 ELF 无防护（elf.rs）
- **文件**: `src/kernel/proc/elf.rs`
- **描述**: ELF 解析器信任文件中的 `e_phoff`、`e_phentsize`、`p_offset`、`p_filesz` 字段。恶意构造的 ELF 可导致内核读取超出文件范围的内存，或让 `p_offset + p_filesz` 整数溢出。
- **影响**: 内核 OOB 读、潜在 RCE（攻击者控制的内核态代码执行）
- **修复建议**: 所有偏移/大小做溢出检查，限制段数上限。

#### C18. 用户态进程内核栈物理地址泄露
- **文件**: `src/kernel/proc/user_proc.rs`
- **描述**: 已修复的 Issue #9 中，内核栈指针使用了物理地址而非虚拟地址。修复后引入了 `KERNEL_BASE` 偏移，但 `destroy()` 路径中的逆向转换如果偏移值有误，会导致 `pmm_free_page` 释放错误的物理页。
- **影响**: 释放随机物理页 → 内核崩溃
- **修复建议**: 使用统一的 phys_to_virt/virt_to_phys 函数而非手动加减。

#### C19. scheduler 的 load_balance 无迁移限制
- **文件**: `src/kernel/proc/scheduler.rs`
- **描述**: 负载均衡时无条件迁移任务，不考虑任务的缓存亲和性（cache hotness）。频繁迁移导致高比例的 cache miss。
- **影响**: 严重性能退化（30-50%）
- **修复建议**: 引入迁移冷却期（migration cooldown），任务必须在当前 CPU 运行至少一个时间片后才可迁移。

#### C20. fork() 后子进程文件描述符表浅拷贝
- **文件**: `src/kernel/proc/process.rs`
- **描述**: fork 复制文件描述符表时仅复制句柄而非底层 `File` 对象。父子进程关闭 fd 时各自递减引用计数，但若引用计数本身不是原子的，并发 close 可能双重释放。
- **影响**: UAF、文件系统元数据损坏
- **修复建议**: 确保 File 对象的引用计数使用原子操作，或在 fork/close 路径加锁。

#### C21. 进程 PID 分配器回绕无检测
- **文件**: `src/kernel/proc/process.rs`
- **描述**: PID 分配使用简单递增计数器，回绕到 0 时不检查是否与现有进程冲突。当 PID 空间耗尽并回绕时，可能分配已存在的 PID。
- **影响**: 信号发送到错误的进程、kill 误杀
- **修复建议**: 回绕时检查 `pid_in_use(pid)`，跳过已被占用的 PID。

#### C22. CFS enqueue vruntime 初始化错误
- **文件**: `src/kernel/proc/cfs.rs`
- **描述**: 新进程入队时 `vruntime` 从 `min_vruntime` 起步，但如果系统负载高且 `min_vruntime` 很大，新进程会获得过多的 CPU 时间（补偿过度）。
- **影响**: 调度公平性破坏，fork bomb 可获取大量 CPU
- **修复建议**: 使用 `max(min_vruntime, se->vruntime)` 而非固定的 min_vruntime。

#### C23. 调度器 tick() 中的竞态
- **文件**: `src/kernel/proc/scheduler.rs`
- **描述**: `tick()` 中检查 `need_reschedule` 标志和实际调用 `schedule()` 之间存在窗口。在此期间若中断处理修改了运行队列，会导致刚被选中的进程在错误状态被调度。
- **影响**: 调度到已阻塞/退出的进程 → 内核崩溃
- **修复建议**: tick() 中禁用中断或在关键区域使用锁。

#### C24. OOMD 实际未杀死进程
- **文件**: `src/kernel/proc/oomd.rs`
- **描述**: OOM daemon 在 `Emergency` 级别下仅设置 `signal_pending`，但没有实际调用 `proc_kill()` 或发送 SIGKILL。设置信号后也不会在调度循环中检查。
- **影响**: 内存耗尽时系统不释放内存 → 完全死锁
- **修复建议**: 实现完整的 OOM killer 逻辑：选择受害者 → SIGKILL → 等待回收。

#### C25. thread 退出后栈未释放
- **文件**: `src/kernel/proc/thread.rs`
- **描述**: 线程退出时（`thread_exit()`），为其分配的内核栈物理页未被释放回 PMM。
- **影响**: 长期运行后物理内存泄漏
- **修复建议**: 在 thread 清理路径中调用 `pmm_free_page(kstack_phys)`。

#### C26. cpu_queue 中空队列取任务未检查
- **文件**: `src/kernel/proc/cpu_queue.rs`
- **描述**: `cpu_queue_pop()` 在队列为空时可能返回 wild pointer。调用方未检查返回值有效性。
- **影响**: UAF 或空指针解引用
- **修复建议**: 返回 Option<Task>，调用方必须处理 None 情况。

#### C27. 调度器 MLFQ 时间片固定导致饿死
- **文件**: `src/kernel/proc/scheduler.rs`
- **描述**: MLFQ 四级时间片 `[10, 20, 40, 80]` tick 是固定值。第 3 级（80 tick = ~800ms）任务在 CPU 密集型负载下可能长期得不到调度。
- **影响**: 交互式任务响应延迟 ~800ms
- **修复建议**: 已完成 CFS 迁移但是否已全量替换 MLFQ 需要验证。

### 1.3 安全子系统 - CREDO (12 项)

#### C28. SHA256 密码哈希无盐值
- **文件**: `src/kernel/credo/storage.rs`
- **描述**: 用户密码存储为 `SHA256(password)` 纯哈希，无 salt。攻击者可利用彩虹表批量破解。
- **影响**: 密码泄露后可批量还原
- **修复建议**: 使用 `HMAC-SHA256(salt, password)` 并为每个用户生成随机 salt。

#### C29. FirstToken 恢复绕过认证
- **文件**: `src/kernel/credo/bootstrap.rs`
- **描述**: FirstToken（初始信任锚）的恢复路径允许绕过完整的认证链。若攻击者控制设备树，可伪造 FirstToken 获取最高权限。
- **影响**: 完全权限提升
- **修复建议**: FirstToken 使用设备固件中烧录的不可变公钥哈希验证。

#### C30. Capability 委托无深度限制
- **文件**: `src/kernel/credo/capability.rs`
- **描述**: 令牌委托链（delegation chain）无最大深度限制。攻击者可创建极长的委托链，导致遍历时栈溢出。
- **影响**: 内核栈溢出、DoS
- **修复建议**: 设置最大委托深度（如 16），超出则拒绝。

#### C31. Session 密钥材料零化不完整
- **文件**: `src/kernel/credo/session.rs`
- **描述**: Session 销毁时释放内存，但未使用 `zeroize`（覆盖敏感数据后释放）。密钥材料可能残留在 slab 缓存中，被后续分配者读取。
- **影响**: 密钥泄露
- **修复建议**: 使用 `zeroize` crate 或 `volatile_write` 在释放前清零。

#### C32. Audit 日志缓冲区无边界检查
- **文件**: `src/kernel/credo/audit.rs`
- **描述**: 审计日志写入循环缓冲区，但写指针递增时无回绕检查。缓冲区满后越界写入内核内存。
- **影响**: 内核内存损坏
- **修复建议**: 实现环形缓冲区（`write_ptr %= BUF_SIZE`）。

#### C33. Grant 委托中的 TOCTOU
- **文件**: `src/kernel/credo/grant.rs`
- **描述**: `grant_delegate()` 先验证接受方的 capability → 再委托 → 再写入存储。在验证和写入之间存在窗口，接受方的状态可能改变。
- **影响**: 权限提升（接受方在检查后提升权限）
- **修复建议**: 在持锁状态下原子执行验证+委托。

#### C34. Identity 验证中的时序攻击
- **文件**: `src/kernel/credo/identity.rs`
- **描述**: Token 比对使用 `==`（逐字节比较，在第一个差异处返回）。攻击者可通过测量响应时间逐字节猜测正确的 token。
- **影响**: Token 可被侧信道攻击猜测
- **修复建议**: 使用固定时间比较（constant-time comparison）。

#### C35. CREDO FFI 无输入验证
- **文件**: `src/kernel/credo/ffi.rs`
- **描述**: CREDO 的 C FFI 函数接收裸指针和长度参数，但不验证指针是否来自可信调用者，也不检查长度边界。
- **影响**: 任意内核内存读写
- **修复建议**: 验证指针位于用户空间范围内，长度不超过合理上限。

#### C36. 伪随机数生成器可预测
- **文件**: `src/kernel/credo/types.rs`
- **描述**: Token/Nonce 生成缺少 CSPRNG，可能使用可预测的随机源（如 TSC 低位）。
- **影响**: Nonce 重放攻击、Token 可预测
- **修复建议**: 使用硬件随机源（RDRAND）或构建 CSPRNG。

#### C37. Storage 文件完整性无验证
- **文件**: `src/kernel/credo/storage.rs`
- **描述**: CREDO 存储文件（token 数据库）没有完整性校验（MAC/签名）。攻击者可离线篡改存储文件注入恶意 token。
- **影响**: 权限提升
- **修复建议**: 添加 HMAC 或数字签名，启动时验证。

#### C38. 能力检查中的 Short-Circuit 漏洞
- **文件**: `src/kernel/credo/engine.rs`
- **描述**: `check_capability()` 使用逻辑或短路（`||`）连接多个检查条件。若第一个条件过早返回 true 而后续条件更严格，可能导致未充分检查的权限通过。
- **影响**: 权限检查绕过
- **修复建议**: 所有检查条件必须全部通过（使用 `&&` 或显式验证所有条件）。

#### C39. Bootstrap 信任根存储不安全
- **文件**: `src/kernel/credo/bootstrap.rs`
- **描述**: 启动信任锚（Root of Trust）硬编码在源码中。任何能读取内核镜像的攻击者都能获取信任锚的值。
- **影响**: 信任根泄露（可接受的已知风险，但需要在文档中注明）
- **修复建议**: 文档明确标注信任锚不提供硬件级别的安全性。

### 1.4 文件系统 - HvFS (5 项)

#### C40. Checksum 假 SHA256 实现
- **文件**: `src/kernel/fs/hvfs/checksum.rs`
- **描述**: HvFS checksum 模块声称使用 SHA256 进行数据完整性校验，但实际使用简化的或非标准的哈希函数（如 Fletcher 变体）。这不提供密码学级别的完整性保护。
- **影响**: 静默数据损坏无法检测、恶意数据篡改无法识别
- **修复建议**: 使用真正的 SHA256（复用 `credo/sha256.rs`），或明确文档化这是非密码学校验和。

#### C41. ARC 缓存 UAF（Use-After-Free）
- **文件**: `src/kernel/fs/hvfs/arc.rs`
- **描述**: ARC (Adaptive Replacement Cache) 的 eviction 路径在释放 buffer 后未将指针置空。并发访问可能读取已释放的缓存行。
- **影响**: UAF、内核信息泄露
- **修复建议**: 释放后置空指针，或在 eviction 时使用锁保护整个操作。

#### C42. Vdev 双重偏移计算
- **文件**: `src/kernel/fs/hvfs/vdev.rs`
- **描述**: Vdev 的 `vdev_read()`/`vdev_write()` 中偏移量被添加两次（一次在调用方，一次在 Vdev 内部），导致读写错误的磁盘区域。
- **影响**: 数据写入错误位置、文件系统元数据损坏
- **修复建议**: 统一偏移量语义，确保只在一个层级做偏移转换。

#### C43. ZIL replay 中事务顺序不保证
- **文件**: `src/kernel/fs/hvfs/zil.rs`
- **描述**: ZIL（ZFS Intent Log）replay 时按日志记录顺序重放，但未处理事务间的依赖关系。若日志包含交错的事务，replay 可能以错误的顺序应用变更。
- **影响**: 恢复后文件系统状态不一致
- **修复建议**: 按 TXG 分组 replay，同 TXG 内保证顺序。

#### C44. Dataset 引用计数不原子
- **文件**: `src/kernel/fs/hvfs/dataset.rs`
- **描述**: Dataset 的 refcount 操作非原子。在快照创建/销毁与正常 I/O 并发时可能导致 refcount 竞争。
- **影响**: 快照过早释放或永不释放
- **修复建议**: 使用原子操作或锁保护 refcount。

### 1.5 同步原语 (6 项)

#### C45. SpinLockGuard Drop 破坏内存可见性
- **文件**: `src/kernel/sync/spinlock.rs`
- **描述**: `SpinLockGuard` 的 `Drop` 实现中释放锁时不包含 memory barrier。编译器/CPU 可能在释放锁后仍将临界区内的写操作延迟，导致下一个获取锁的 CPU 看不到更新的数据。
- **影响**: 竞态条件、数据不一致
- **修复建议**: 在 drop 中使用 `core::sync::atomic::fence(Ordering::Release)` 或在锁释放时使用 store-release。

#### C46. MutexGuard Drop 同样缺少内存屏障
- **文件**: `src/kernel/sync/mutex.rs`
- **描述**: 同 C45，Mutex 解锁时缺少 Release 语义。
- **影响**: 竞态条件
- **修复建议**: 同 C45。

#### C47. Seqlock 写者无互斥
- **文件**: `src/kernel/sync/seqlock.rs`
- **描述**: Seqlock 假设只有一个写者，但代码中没有机制保证这一点。多写者并发时 seq 可能奇数-偶数-奇数跳跃。
- **影响**: 读者读到损坏数据
- **修复建议**: 在 write_lock 中添加自旋锁或原子 CAS 保护。

#### C48. Seqlock TOCTOU 读者读到脏数据
- **文件**: `src/kernel/sync/seqlock.rs`
- **描述**: 读者在读前读 seq（偶数）→ 读数据 → 读后再读 seq（不匹配则重试）。但前后两次 seq 读取之间没有 compiler fence，编译器可能重排读数据到 seq 检查之前。
- **影响**: 读者读取到未完成写入的数据
- **修复建议**: 添加 `compiler_fence(Ordering::Acquire)` 在两次 seq 读取处。

#### C49. RCU 多核不安全
- **文件**: `src/kernel/sync/rcu.rs`
- **描述**: RCU（Read-Copy-Update）的 grace period 检测依赖 per-CPU 的 quiescent state 检测，但未使用 IPI（核间中断）通知其他 CPU 进入 quiescent state。单核假设在多核下失效。
- **影响**: RCU 保护的指针 UAF
- **修复建议**: 实现完整的 RCU grace period 机制（如 Linux 的 `synchronize_rcu()`）。

#### C50. RCU 无宽限期回调队列
- **文件**: `src/kernel/sync/rcu.rs`
- **描述**: RCU `call_rcu()` 注册的回调在 grace period 结束后没有执行的机制。
- **影响**: 内存泄漏（延迟释放永远不会发生）
- **修复建议**: 实现 `rcu_do_batch()` 在 quiescent state 时调用。

### 1.6 栏栈恢复 (3 项)

#### C51. tick() 中的死锁
- **文件**: `src/kernel/barrier/recovery.rs`
- **描述**: `tick()` 函数在心跳检测中持有 `RECOVERY_LOCK`，然后调用 `bsr_try_recover()`，而后者又尝试获取同一个锁。这是 100% 可触发的递归死锁。
- **影响**: 任何心跳丢失都导致系统完全死锁
- **修复建议**: tick() 中设置标志后释放锁，由独立的内核线程执行恢复。

#### C52. RecoverableMutex 锁顺序反转
- **文件**: `src/kernel/barrier/recoverable.rs`
- **描述**: `RecoverableMutex` 在恢复路径中按域名排序加锁，但正常操作路径使用不同的锁顺序。恢复过程中可能因锁序不一致而死锁。
- **影响**: 恢复失败 → 系统停机
- **修复建议**: 统一所有路径的锁顺序（按域名 ID 升序）。

#### C53. Barrier Snapshot TOCTOU
- **文件**: `src/kernel/barrier/snapshot.rs`
- **描述**: 快照创建先检查 `can_snapshot()` → 再创建快照。检查与创建之间存在 TOCTOU 窗口，恢复域状态可能在此期间改变。
- **影响**: 快照数据不一致，回滚不完整 → 恢复后状态错误
- **修复建议**: 在持锁状态下原子执行检查+快照。

### 1.7 驱动与设备 (8 项)

#### C54. VGA 帧缓冲裸指针直接访问
- **文件**: `src/kernel/driver/char/vga.rs`
- **描述**: VGA 文本模式缓冲区使用硬编码物理地址 `0xB8000` 直接写入。在启用分页后，该物理地址未被映射到虚拟地址空间，写入会导致 page fault。
- **影响**: 内核崩溃（如果 VGA 未映射）
- **修复建议**: 使用 ioremap 将 `0xB8000` 映射到虚拟地址后再访问。

#### C55. DMA map_single 悬垂指针
- **文件**: `src/kernel/dma/engine.rs`
- **描述**: `map_single()` 获取 Mutex 锁 → 在锁内构造映射 → 返回映射中的指针 → 释放锁。调用方使用返回的指针时 Mutex 已解锁，底层数据可能被并发修改。
- **影响**: UAF、DMA 写入错误内存
- **修复建议**: 不在 map_single 内部持锁时返回内部指针；或将生命周期绑定到 guard。

#### C56. NVMe PRP2 始终为零
- **文件**: `src/kernel/driver/storage/nvme.rs`
- **描述**: NVMe 命令的 PRP2 条目在处理多页传输时未被设置，始终为 0。导致超过 4KB 的 DMA 传输的第二页数据写入物理地址 0。
- **影响**: 数据损坏（覆盖 IVT/中断向量表等关键低地址内存）
- **修复建议**: 正确填充 PRP2 指向第二页的物理地址。

#### C57. PageFault RIP += 2 硬编码
- **文件**: `src/kernel/idt/handlers.rs`
- **描述**: Page fault handler 中 `frame.rip += 2` 是硬编码的指令长度，用于跳过触发缺页的指令。但 x86 是变长指令集，指令可能为 1-15 字节。错误的跳过将导致执行垃圾指令。
- **影响**: 未定义行为（执行随机数据）
- **修复建议**: 实现指令长度解码器，或使用 x86 LDT 机制（如 `#PF` 返回时自动重试）。

#### C58. ATA 驱动无超时处理
- **文件**: `src/kernel/driver/storage/ata.rs`
- **描述**: ATA PIO 读写在 `while (status & BSY)` 中自旋等待，无超时机制。若设备不响应（如磁盘故障），系统永久挂起。
- **影响**: 系统死锁
- **修复建议**: 添加超时计数器，超时后返回错误。

#### C59. PCI 枚举未验证 BAR 类型
- **文件**: `src/kernel/driver/bus/pci.rs`
- **描述**: PCI BAR（Base Address Register）读取后直接作为 MMIO 地址使用，未检查 BAR 类型（Memory vs I/O）和是否为 64-bit BAR。
- **影响**: 访问无效地址或 I/O 端口
- **修复建议**: 检查 BAR 位 0（Memory/I/O 标志）和位 2-1（32/64-bit）。

#### C60. USB xHCI 无错误恢复
- **文件**: `src/kernel/driver/usb/xhci.rs`
- **描述**: xHCI 控制器在传输错误后不执行错误恢复流程（ring dequeue pointer 复位）。后续传输使用损坏的 ring 状态。
- **影响**: USB 子系统永久不可用
- **修复建议**: 实现 xHCI error ring recovery。

#### C61. VirtIO 队列描述符耗尽无处理
- **文件**: `src/kernel/driver/virtio/queue.rs`
- **描述**: VirtIO 队列描述符用完时不返回错误，后续分配会覆盖正在使用的描述符。
- **影响**: DMA 传输损坏
- **修复建议**: 耗尽时返回错误或阻塞等待描述符释放。

### 1.8 网络栈 (5 项)

#### C62. lwIP NO_SYS 模式下的中断竞态
- **已知问题 #1**: `src/kernel/net/init.rs`
- **描述**: lwIP 在 NO_SYS 模式下运行（无 tcpip_thread），定时器 ISR 和网卡中断 ISR 并发访问 lwIP 内部数据结构。虽有 CLI/STI 保护 `lwip_init()`，但运行期间的并发风险仍然存在。
- **影响**: 网络栈数据结构损坏、内核崩溃
- **修复建议**: 长期方案 — 迁移到 lwIP 的 `tcpip_thread` 模式。

#### C63. virt_to_phys 假恒等映射
- **文件**: `src/kernel/net/sys_arch.rs`
- **描述**: lwIP 的 `sys_arch` 适配层中 `virt_to_phys()` 返回恒等值（`addr as u32`），假设虚拟地址等于物理地址。在高半内核中这完全错误。
- **影响**: DMA 写入错误的物理地址 → 内核内存损坏
- **修复建议**: 实现真正的 virt_to_phys 转换（查询页表或使用内核直接映射区域的固定偏移）。

#### C64. LWIP_RAND() 使用常量
- **文件**: `src/kernel/net/lwip/lwipopts.h`
- **描述**: 配置中 `LWIP_RAND()` 可能返回常量（取决于配置），破坏 TCP 序列号随机化、DHCP xid 随机化、DNS 事务 ID 随机化。
- **影响**: TCP 劫持、DHCP 欺骗
- **修复建议**: 将 `LWIP_RAND()` 连接到真正的随机源。

#### C65. e1000 驱动无接收队列溢出保护
- **文件**: `src/kernel/net/driver/e1000.rs`
- **描述**: e1000 接收描述符 ring 用完后，新到达的包被丢弃。但在高负载下，描述符回收不及时，导致大量丢包且无统计。
- **影响**: 网络中断（包黑洞）
- **修复建议**: 增加 ring 大小或实现 NAPI 风格轮询。

#### C66. 网络缓冲区 pbuf 在中断上下文中分配
- **文件**: `src/kernel/net/sys_arch.rs`
- **描述**: 网卡中断 ISR 中调用 `pbuf_alloc()` 分配内存（通过 `kmalloc`）。如果 kmalloc 内部使用锁，在中断上下文中可能导致死锁。
- **影响**: 中断死锁 → 内核挂起
- **修复建议**: 预分配接收缓冲区池，ISR 中不分配内存。

### 1.9 WASM 运行时 (3 项)

#### C67. WASM i32::MIN / -1 未 Trap
- **文件**: `src/kernel/wasm/interpreter.rs`
- **描述**: WASM 规范规定 `i32.div_s(i32::MIN, -1)` 必须 trap（溢出）。当前实现直接执行硬件除法，产生未定义的 CPU 异常。
- **影响**: 违反 WASM 规范、沙箱逃逸隐患
- **修复建议**: 除法前检查操作数，触发 trap。

#### C68. WASM 内存边界检查遗漏
- **文件**: `src/kernel/wasm/interpreter.rs`
- **描述**: `i32.load`/`i32.store` 的内存边界检查使用 `addr + offset + size > mem_size`，但如果 `addr + offset` 溢出回绕，可能通过检查却访问越界内存。
- **影响**: 沙箱逃逸（读取内核内存）
- **修复建议**: 使用饱和加法或分别检查 overflow。

#### C69. WASM Gas Metering 无强制执行
- **文件**: `src/kernel/wasm/runtime.rs`
- **描述**: Gas metering（燃料计量）在循环回边处递减，但未检查函数调用和内存操作的开销。无限递归或大量内存操作可能绕过 gas 限制。
- **影响**: DoS（WASM 模块消耗无限内核资源）
- **修复建议**: 每个操作码执行前检查 gas，不足则 trap。

### 1.10 构建系统与链接脚本 (4 项)

#### C70. 链接脚本 .rela.dyn 无 PHDR 段
- **文件**: `src/kernel/link/x86_64.ld`, `src/link.ld`
- **描述**: `.rela.dyn`、`.dynsym`、`.dynstr` 段没有 PHDR 声明（`:boot` 或 `:kernel`），运行时不会被 PT_LOAD 覆盖，不会被加载到内存。内核使用 `-fPIC` 编译，依赖这些段进行重定位。
- **影响**: 运行时段重定位时读取未加载的内存 → 未定义行为
- **修复建议**: 添加 `:kernel` PHDR 声明到这些段。

#### C71. AArch64 链接脚本缺失重定位段
- **文件**: `src/kernel/link/aarch64.ld`
- **描述**: AArch64 的链接脚本完全没有 `.rela.dyn`、`.dynsym`、`.dynstr` 段。
- **影响**: AArch64 内核运行时崩溃
- **修复建议**: 如果 AArch64 不使用 PIC，则移除 `-fPIC`；如果使用，则添加这些段。

#### C72. 双链接脚本不一致
- **文件**: `src/link.ld` vs `src/kernel/link/x86_64.ld`
- **描述**: 项目根目录的 `src/link.ld` 和 `src/kernel/link/x86_64.ld` 内容不同：
  - `x86_64.ld` 包含 `*(.trampoline)` 段和 `__boot_text_end` 符号
  - `src/link.ld` 缺少这些
- **影响**: 不确定哪个是活跃脚本，可能导致链接错误
- **修复建议**: 删除废弃的 `src/link.ld`，统一使用 `src/kernel/link/x86_64.ld`。

#### C73. 链接脚本无 BSS 结束符号
- **文件**: `src/kernel/link/x86_64.ld`, `src/kernel/link/aarch64.ld`
- **描述**: 仅有 `__bss_start`，缺少 `__bss_end`。BSS 清零代码无法知道清零范围。
- **影响**: BSS 可能未完全清零 → 未初始化变量的随机值
- **修复建议**: 添加 `__bss_end = .;`。

### 1.11 用户态程序 (3 项)

#### C74. axsh Shell 命令注入
- **文件**: `src/user/axsh/src/commands/system.rs`
- **描述**: Shell 的 `system()` 命令接受用户输入后传递给内核 `exec()` 系统调用。用户可注入任意命令（如 `; rm -rf /`），在单用户系统中虽受限但仍是不良实践。
- **影响**: 潜在的恶意命令执行
- **修复建议**: 对输入做白名单校验。

#### C75. install 向导密码明文传输
- **文件**: `src/user/install/src/wizard/auth.rs`
- **描述**: 安装向导收集密码后通过系统调用原样传递给内核。密码在系统调用参数中（通过寄存器）明文传输。
- **影响**: 密码泄露（如果系统调用被追踪/拦截）
- **修复建议**: 客户端先对密码做哈希后再传递给内核。

#### C76. httpsrv 无请求大小限制
- **文件**: `src/user/httpsrv/src/main.rs`
- **描述**: HTTP 服务器读取请求体时不限制大小。攻击者可发送 GB 级请求体导致服务器进程 OOM。
- **影响**: DoS（用户态 HTTP 服务器崩溃）
- **修复建议**: 添加 Content-Length 检查和请求体大小上限。

### 1.12 IPC (4 项)

#### C77. 共享内存物理地址暴露给用户态
- **文件**: `src/kernel/ipc/shm.rs`
- **描述**: `shm_create()` 返回的共享内存标识包含底层物理地址信息。用户态可以推断内核内存布局。
- **影响**: 内核 ASLR 绕过（如果有）、信息泄露
- **修复建议**: 使用不透明的 shm_id 而非包含物理地址的结构。

#### C78. 全局 IPC 命名空间无锁并发
- **文件**: `src/kernel/ipc/mod.rs`
- **描述**: 全局 IPC 对象表（管道、消息队列、信号量、共享内存）没有统一的锁保护。并发创建/销毁 IPC 对象导致表损坏。
- **影响**: IPC 对象混乱、UAF
- **修复建议**: 对全局 IPC 表加锁或使用无锁数据结构。

#### C79. 信号发送不做权限检查
- **文件**: `src/kernel/ipc/signal.rs`
- **描述**: 任意进程可向任意其他进程发送信号（包括 SIGKILL），不检查发送者的权限。
- **影响**: 任意进程可杀死任意其他进程
- **修复建议**: 检查发送者是否为 root 或与目标进程同 UID。

#### C80. 管道缓冲区溢出无处理
- **文件**: `src/kernel/ipc/pipe.rs`
- **描述**: 管道写满时不阻塞写入者也不返回错误，直接覆盖旧数据。
- **影响**: 数据静默丢失
- **修复建议**: 写满时阻塞写入者（等待读者消费）或返回 EAGAIN。

### 1.13 文档 (8 项)

- **描述**: 文档中描述的系统调用编号与实际实现完全不同。例如文档写 `SYS_FS_OPEN = 20`，代码中是 `SYS_open = 2`（POSIX 标准编号）。

#### C82. kernel-architecture.md 描述 C 版本内核

## 七、总体评估

### 优势
- **架构设计清晰**: 子系统分层合理，模块职责明确
- **创新性强**: Barrier 栏栈、CREDO 权限模型、HvFS v2 均为原创设计
- **测试覆盖良好**: host-tests + kernel-tests 覆盖核心路径
- **双架构支持**: x86_64 和 AArch64 均已构建通过
- **代码风格一致**: Rust 代码整体遵循良好惯例

### 主要风险领域
1. **并发安全**: 锁语义不完整、RCU 多核不安全、PMM 无锁 → SMP 环境风险高
2. **数据完整性**: 假 SHA256、NVMe DMA 错误、链接脚本缺陷 → 静默数据损坏
3. **文档债务**: 核心文档（syscall、架构）与代码完全脱节 → 误导开发
4. **网络栈安全性**: `virt_to_phys` 假恒等 + NO_SYS 竞态 → 运行时可靠性差
5. **WASM 沙箱**: 边界检查遗漏 + 除法未 trap → 沙箱逃逸隐患
