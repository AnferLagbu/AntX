# docs/ 写作规范

> 本目录的结构: `CHANGELOG.md` (版本变更) + `plan/` (计划/历史) + `explain/` (现状/解释).
> 本文件告诉开发者**往这三处写入/修改时的格式与组织要求**.

> **适用范围:** 本文件定义的所有格式规则**仅适用于 `docs/` 下文档** (`CHANGELOG.md`, `plan/*`, `explain/*`).
>
> **AGENTS.md / CLAUDE.md 是规则/指导文档, 不受本规范约束, 保持自然描述风格** (用 H1/H2/H3 + 表格 + 代码块 + 列表自由组织, 不强制"每条带状态 [X]/[]"). 详见 `AGENTS.md` §7.

---

## 0. 核心原则 (最重要, 先看)

| 原则 | 含义 |
|------|------|
| **格式极简** | 纯 Markdown, 无模板, 无前置 front-matter, 无目录页. 标题用 `#` 一级起, 章节用 `##` 即可. |
| **信息密度高** | 该写的一句不少, 不该写的一句不留. 没有占位符, 没有"TODO: 补充". 不确定的就写"未知". |
| **结构自洽** | 每个文件完整讲清楚一件事. 不依赖其它未链接文件即可读. 跨文件引用用相对路径. |
| **中文优先** | 文档用中文写. 专有名词 (API/术语) 保留英文. 代码示例保留英文. |
| **可搜索** | 关键词首次出现时加粗一次, 之后不重复加粗. |

不要做的事:
- 不写"前言 / 摘要 / 致谢"等空话.
- 不在文档中嵌入大段完整代码 (代码应指向源文件, 引用行号).
- 不创建无人维护的索引页.
- 不为"将来可能用到"预留章节.

## 1. 文件归属规则 (写之前先看)

| 写什么 | 放哪里 | 文件名 |
|--------|--------|--------|
| 一次提交的变更说明 | `docs/CHANGELOG.md` (累积到 `[Unreleased]` 段) | 固定 |
| 路线图 / 未来计划 | `docs/plan/` | `*.md` |
| 设计计划 / 迁移方案 | `docs/plan/` | `*.md` |
| 审计报告 / 修复报告 / 交付总结 | `docs/plan/` | `audit-*.md` / `fix-report-*.md` / `delivery-summary-*.md` |
| 待办 (跨多 commit) / 已知问题 | `docs/plan/` | `fix-tasks.md` / `known-issues.md` |
| 架构说明 / 子系统文档 | `docs/explain/` | `*.md` |
| API 参考 / 教程 | `docs/explain/` | `*.md` |
| 论文 / 设计文档 / 参考材料 | `docs/explain/` | `*.md` |

判断口诀:
- 这东西**指向未来**或**记录历史**? → `plan/`
- 这东西**解释现在**或**教人使用**? → `explain/`
- 这东西是**当前这次提交**的变更? → `CHANGELOG.md`

---

## 2. 文件命名规则

- 全小写 + 连字符 (`kebab-case`).
- 单词之间用 `-`, 不用 `_` 或空格.
- 文件名**不带日期前缀** (日期写在文件内部, 见 §3).
- 同一主题多个文件用统一前缀 (例: `audit-*`, `fix-report-*`).
- 例: `framekernel.md` ✓, `FRAME_KERNEL.MD` ✗, `FrameKernel-roadmap.md` ✗.

## 3. 文档内部格式

### 3.1 通用结构

> 文档 = 标题 + 若干章节, 每章节 = 条目列表, 每条目 = 描述 + 方案 + 状态.
> 状态: `[]` = 未实施, `[X]` = 已实施.
> 详情: 可选, 必要时补充深入内容 (代码片段/数据/参考链接).

```
# <文档标题>

> 0-1 行核心结论. 没想清楚就空着.

## <章节 1>
- **<条目名>**
  - 描述: <描述>
  - 方案: <如何做>
  - 状态: []
  - 详情: <可选, 深入内容>

- **<条目名>**
  - 描述: <描述>
  - 方案: <如何做>
  - 状态: [X]

## <章节 2>
- **<条目名>**
  - 描述: <描述>
  - 方案: <如何做>
  - 状态: []
  - 详情: <可选, 深入内容>
```

### 3.2 格式细则

| 元素 | 规则 |
|------|------|
| 标题 | H1 用一次, H2 章节, H3 子章节. 不用 H4 及更深. |
| 列表 | 用 `-` 无序列表. 不用 `*` 或 `+`. 嵌套缩进 2 空格. |
| 代码 | 用围栏 ``` + 语言标识. 行内用 ` 单引号. |
| 表格 | 用 GFM 表格. 列对齐只在数字列用 `---:`. |
| 引用 | 用 `>`. 跨文件引用用相对路径: `[标题](./other.md)`. |
| 强调 | 关键词首次出现 `**加粗**`. 不用斜体. |
| 链接 | 优先用相对路径. 外部 URL 完整给出. |
| 图片 | 不建议用. 必要时 `![alt](./img/x.png)`, 图片放同目录 `img/`. |
| 日期 | 写绝对日期 `YYYY-MM-DD`, 不写"昨天/最近/即将". |
| 数字 | 大于 1000 加千分位. 代码中的数不加. |
| 缩写 | 首次出现展开: "宏内核 (Monolithic Kernel, MK)". |

### 3.3 代码引用

不复制大段代码. 用以下形式指向源:

```
详见 [src/kernel/framework/proc/user_proc.rs:810-858](src/kernel/framework/proc/user_proc.rs) 的 `create()` 函数.
```

或在行内:

```rust
// user_proc.rs:820
let cr3_val = setup_pagetable(kproc);
```

引用代码**必须真实存在**, 引用前请先 `grep` 确认行号.

## 4. CHANGELOG.md 格式

只此一份, 不分文件. 累积式追加, 永不删除历史.

**项目无项目级版本号** (5月21日 `df0cb83` 已移除), commit 消息中的 `vX.Y` 是**子特性/子系统的内部代号** (如 Issue1 v2.30, HvFS v2, PWID v5), **不是**项目版本号, 不要在 CHANGELOG 节标题中编造项目版本.

按**日期**分段, 时间倒序:

```
## [Unreleased]

### 新增
- (条目)

### 变更
- (条目)

### 修复
- (条目)

### 移除
- (条目)

## 2026-06-06

### 新增
- ...
```

子节固定 4 类 (新增 / 变更 / 修复 / 移除), 可选: `### 决策 (DECISION-NNN)` 和 `### 关键 commit 索引` (表格).

条目格式:
- 一行一个, 以动词开头: "新增 / 变更 / 修复 / 移除 / 重命名 / 重构".
- 句末不写句号.
- 引用 commit/issue/PR 用 `(commit abc1234)` 或 `(#123)`.
- 安全/兼容性相关条目加粗: `**BREAKING**: ...`.
- 提到子特性代号时, 用括号注明"特性内部版本"避免误读, 例: `(特性代号 PWID v5)`.

日期选定规则:
- 一节内的 commits 都集中在一天 → 用那一天 (`## 2026-06-06`).
- 跨多天但属于同一主题 → 用最后一天的日期, 在主题行注明跨度.
- 模糊的"上个月" → 用月初 (`## 2026-05-31` 表示 5 月内累积) 即可, 不必精确到日.

后续若要引入项目级版本号:
- 需先开 DECISION-NNN 记录, 写入 `docs/plan/`, 再切换 CHANGELOG 标题格式.

## 5. plan/ 文档格式

主题: 计划/未来/历史决策. 重点是**意图、约束、状态**.

> 一个文档允许包含多个工程计划. 每个工程计划 = 独立 H2 章节, 章节标题 = 计划名.
> 状态: `[]` = 未实施, `[X]` = 已实施. 详情: 可选, 必要时补充深入内容.

```
# <文档标题>

> 0-1 句话说清"为什么有这个计划 / 历史上发生了什么".

## 工程计划 A: <计划名>
### 背景
- **<背景条目>**
  - 描述: <为何要做 / 触发了什么>
  - 方案: <应对思路>
  - 状态: []

### 目标
- **<目标条目>**
  - 描述: <具体要达到什么>
  - 方案: <如何达成>
  - 状态: []

### 现状 (YYYY-MM-DD)
- **<现状条目>**
  - 描述: <已完成什么 / 未完成什么>
  - 方案: <下一步动作>
  - 状态: []

### 方案
- **<方案条目>**
  - 描述: <实现思路关键决策点>
  - 方案: <具体步骤>
  - 状态: []
  - 详情: <可选, 关键设计点/参考链接>

### 待办
- **<待办条目>**
  - 描述: <具体可执行项>
  - 方案: <如何做>
  - 状态: []

### 决策记录
- **DECISION-NNN**
  - 描述: <决策内容>
  - 方案: <原因, 替代方案及放弃原因> (YYYY-MM-DD)
  - 状态: [X]

### 变更历史
- **YYYY-MM-DD**
  - 描述: <条目>
  - 方案: -
  - 状态: [X]

## 工程计划 B: <计划名>
### 背景
- **<背景条目>**
  - 描述: ...
  - 方案: ...
  - 状态: []
```

要点:
- 一个文档允许包含多个工程计划. 每个工程计划用 H2 章节独立, 章节标题 = `工程计划 <ID>: <名称>`.
- H2 章节下用 H3 子章节 (背景/目标/现状/方案/待办/决策记录/变更历史) 组织条目.
- 同一文档内多个工程计划应: (1) 主题相关, (2) 互不冲突, (3) DECISION-NNN 全文档编号唯一.
- 计划随时间变化, 改文档本身. **不创建 `*-v1.md` `*-v2.md`**.
- 已完成 / 已废弃的计划**保留**, 在状态字段标记, 不删除.
- 决策记录 (DECISION-NNN) 一旦写入, 编号永久保留, 不重用 (全文档唯一).

## 6. explain/ 文档格式

主题: 解释现在. 重点是**是什么、为什么、怎么用**.

```
# <文档标题>

> 0-1 句话说清"这篇文档讲什么 / 谁需要看".

## 这是什么
- **<定义条目>**
  - 描述: <定义, 范畴>
  - 方案: <如何界定>
  - 状态: [X]

## 为什么这样设计
- **<设计条目>**
  - 描述: <设计动机, 关键约束>
  - 方案: <替代方案及放弃原因>
  - 状态: [X]

## 如何使用
- **<使用条目>**
  - 描述: <API 速查 / 操作步骤 / 代码示例>
  - 方案: <典型场景>
  - 状态: [X]

## 工作原理 (可选)
- **<原理条目>**
  - 描述: <内部机制, 深入内容>
  - 方案: <关键路径>
  - 状态: [X]

## 注意事项
- **<注意条目>**
  - 描述: <坑 / 限制 / 性能特征 / 安全考量>
  - 方案: <规避方法>
  - 状态: [X]

## 交叉引用
- **依赖**
  - 描述: [xxx](./xxx.md)
  - 方案: -
  - 状态: [X]

- **被引用**
  - 描述: ...
  - 方案: -
  - 状态: [X]
```

要点:
- 写"现在是这样", 不用"将来会改成那样".
- 删了/改了代码, 文档同步改. 文档失实比缺文档更糟.
- 多文件存在时, 拆成多个独立 `*.md`, 用相对链接互引, **不做总目录页**.

## 7. 修改现有文档

- 小修: 直接改, 改完在文档底部"变更历史"加一行 (`YYYY-MM-DD: 简述`).
- 大改 (结构调整 / 重写): 在文档顶部 `<>` 标记后, 写一行 `> **重写 YYYY-MM-DD**: 简述改动原因`.
- 推翻: 在文档顶部加 `> **DEPRECATED YYYY-MM-DD**: 废弃原因. 见 [新文档](./new.md)`. 不删除.

## 8. 自检清单 (提交前过一遍)

- [ ] 文档归属正确 (CHANGELOG / plan / explain)?
- [ ] 文件名 `kebab-case`, 无日期前缀?
- [ ] H1 仅一个, H2 起章节, 无 H4+?
- [ ] 代码引用行号已用 `grep` 验证?
- [ ] 跨文件链接用相对路径且目标存在?
- [ ] CHANGELOG 条目动词开头, 无句末句号?
- [ ] plan 文档状态字段已更新?
- [ ] explain 文档与代码现状一致?
- [ ] 文档底部"变更历史"已加本次日期?

## 9. 反例 (不要这样写)

不要写前言:
```
# 内核架构文档

本项目是一个创新的宏内核操作系统, 由本团队自主研发, ...
> 前言段不是规范要求, 是冗余.
```

不要写空模板:
```
## 概述
(待补充)

## 详细设计
(待补充)
```

不要在文档里粘大段代码:
```
下面是 xxx 函数的完整实现:
\`\`\`rust
fn foo() {
    // 200 行 ...
}
\`\`\`
```
(应改为指向源文件链接 + 1-3 行关键片段)

不要写"将来"而不写日期:
```
> 未来我们将支持 ...
```
(应改为 "计划在 v3.0 (2026-Q3) 引入 ..." 或删除)
